# 移动端通用走读与验收

## 追踪实际链路

1. 拆出要回答的问题，从用户提供的类名、页面、接口、日志、配置键或资源定位入口。向上追实际调用方和触发源，向下追分支、状态写入、后续调用和失败处理。对关键方法说明输入、返回、提前退出条件与副作用。
2. 按需追数据流：请求参数来源、响应模型、缓存键和有效期、状态消费、线程和异步回调。区分未请求、数据未被消费、界面未展示。接口声明、占位实现和未接通的注册点要分别标注。
3. 按需追配置与生命周期：默认值、下发与就绪时机、实验归属、权限、初始化、账号或页面切换、重试和频控。代码里读取开关只能证明读取逻辑，实际命中以配置或设备证据为准。
4. 涉及弹窗时，拆开业务触发、框架展示、队列、频控和真实互斥。沿实际展示入口核对普通与立即展示、稳定 ID、排队、释放、关闭和丢弃回调。涉及 RN/KRN 或其他动态容器时，追路由参数、容器选择、bundle 与加载失败回退。未找到页面代码时明确搜索范围。
5. 做需求分析时，先列当前行为、需求触发和期望变化，再给最小改动点、上下游契约、回归场景和待定口径。跨版本或平台对齐时，将需求约定、参考端实际行为和目标端已接通的实现分别列明。用户只要求分析时保持目标项目只读。

## 需求文档与交互功能分析

分析需求文档并对照源码时，先列出文档约定，再核对实际行为。涉及交互展示时，把以下适用项写入交付：

- **触发时机**：分别说明谁触发、什么事件触发、在什么页面与生命周期阶段生效、需要哪些人群或配置条件。拆开业务触发、数据准备、请求展示、框架排队或拦截、实际展示、曝光及后续重试。按实际顺序画 ASCII 图，标出异步边界及未命中、取消、失效、重复触发的结果。
- **关联功能与影响范围**：列出直接触发方、共用框架、配置与数据提供方、下游消费者，以及与同场景功能的互斥、并发或回归关系。对每项说明关联原因、调用方向和源码证据，区分实际接通、仅有定义和待验证。
- **弹窗唯一标识**：涉及弹窗治理、埋点、队列去重或跨端配置时，应从业务创建处追踪标识的生成、赋值、传播和消费。分别核对业务稳定 ID、动态模板 ID、登录来源或配置 ID，以及单次展示实例或请求 ID。写清每种标识的唯一性范围、跨版本稳定性、匹配优先级、缺失和冲突处理，以及治理、去重、重放、监控各自用哪个字段。
- **标识设计**：需要提出新设计时，优先复用可验证的稳定业务 ID；不足时定义业务命名空间、组件类型和业务名，例如 `Growth_Popup_SignIn`。同一业务弹窗跨请求保持同一个业务 ID，必要时另设实例 ID 区分并发或重放。说明既有 ID 如何兼容、动态模板如何映射，以及空值和同名冲突的验收方式。类名、模板 ID 或配置 ID 只有在其唯一性范围经过核对后才能承担对应职责。

## 框架级治理与覆盖范围

分析统一拦截、全局治理或公共框架时，先梳理被治理对象的构造参数、实例状态、生命周期、扩展点和类型分流。沿真实代码验证「初始化注册 → 写入框架配置 → 展示入口消费 → 拦截或回调 → 实际结果」；找到注册列表和展示入口后，继续确认两者如何装配。

区分框架入口覆盖、规则实际命中以及队列或状态的作用范围。说明各类业务如何接入、是否有直接展示或其他绕行路径，并区分请求、放行、实际展示和曝光。对于多级队列，分别说明保存的对象、入队条件、顺序和恢复时机。交付时优先在策略细节前给对象职责表、ASCII 总图及装配关键代码。覆盖未经核实的入口要标注待验证。

**覆盖验收**：分别列出需求纳入范围与框架实际可覆盖范围。按项目实际存在的展示路径逐项核对「业务入口或路由 → 最终容器 → 公共展示入口 → 拦截器 → 可匹配 ID」，用覆盖表记录已证实接入、已证实绕行和待核实的落点。同一种展示技术有多条路径时分行记录。若需求范围之外存在可能复用公共框架的路径，至少核查一条。进入拦截链与实际命中规则分别标注，共享 ID 的误匹配范围需单独说明。

## 约束来源与执行方式

分析需求或总结技术文档时，对会影响功能结果的关键约束逐项说明「控制什么、规则从哪里来、判断数据从哪里来、谁在何时执行、命中后怎么处理」。适合比较时使用「控制项｜规则来源｜运行数据来源｜生效与执行方式」表，并在表旁附关键源码摘录。

- **区分来源**：分别核对需求约定、客户端写死的规则或兜底值、远端配置与实验、客户端事件或持久状态，以及接口返回的业务结果。同一个控制项可能同时依赖远端阈值和本地数据，应分别指出读取位置、字段和数据更新时机。
- **写清生效与优先级**：说明配置默认值和生效条件、多个规则同时命中时的顺序、缺失或未就绪时的回退、失败后的处理，以及业务局部规则和框架通用规则是否分别执行。
- **明确接口职责和证据边界**：根据实际请求、响应字段及调用时机判断接口是否提供规则、内容或资格确认。默认值、演算值和实际线上值分别标注。没有运行证据时说明待核实项。

## 详细源码走读

用户要求详细分析、独立阅读或据此复刻行为时，交付应让读者预测指定输入经历哪些分支、改变什么状态、由哪个事件触发下一步。

- **真实入口**：从实际调用者追到注册或装配条件，指出生效页面、构建变体或调用场景。区分源码中存在的能力与已经接通的路径。
- **分支顺序**：按执行顺序写清关键方法的输入、判断、提前返回、返回值、状态变化和后续调用。用调用链或决策表显示优先级，以及前面命中后哪些检查会跳过。
- **状态读写**：对影响行为的状态列出初始值、读写位置、重置时机和保留范围。区分配置默认值、进程或会话状态、持久数据和业务完成结果。
- **事件演算**：选适用的正常、边界和失败场景，逐步列出事件、关键输入、状态前后值、决策结果及下一次触发点。假设值标为示例。重点检查阈值等号、配置迟到、异步失败和生命周期切换等适用边界。
- **就近给证据**：把简化代码、方法名和文件位置放在对应解释旁。区分源码证实、推断及需配置或运行时验证的结论。若只看到定义或接口声明，明确能追到的最后一层。
- **在线文档须能独立验证关键结论**：当本地源码链接无法跳转时，在关键结论旁贴出足以验证它的最小必要代码，并标明文件名、方法和行号。涉及跨文件调用、默认参数、参数转换或状态传播时，按执行顺序摘录代码，保留决定结论的实参、掩码、判断、赋值及消费位置。原样代码标为「源码摘录」，省略或重组的代码标为「简化摘录」。路径和行号作为定位线索，正文须包含支撑结论的代码。

## 行为迁移验收

当用户指定现有平台实现为迁移基线时，用已核实的真实行为编写对齐规格。需求材料用于理解背景；源码差异、兼容行为和拟修正项分别记录。未经确认的修正不能写成基线行为。

- **请求与队列交接**：对每层队列或等待机制核对谁入队、保存什么、如何排序去重、何时出队、由谁重新发起。追到接收方的回调和状态变化。分别确认重新排队、前置拦截、宿主失效和业务拒绝后，原请求与临时重放标记如何处理。
- **退出与生命周期**：逐项追踪取消、宿主销毁、退后台、切账号、配置或实验变化、入口重置和进程重启等适用事件。对等待项、在途请求、计数和缓存写清清理、保留或重置范围。没有找到清理调用方时，说明查证范围与待验证项。
- **阻塞与异步回包**：核对队首不满足、失效或规则变化时是否会阻塞后续请求；区分原地等待、出队但不推进、出队后继续检查。追踪拒绝、失败和迟到回包，并核对回调是否重新检查当前页面、账号、配置及请求身份。
- **标识与兼容边界**：按匹配、去重、重放、接口和监控列出实际字段。验证缺失 ID、共享 ID、同一请求命中不同规则及同业务并发。若建议更换标识，单列它造成的行为差异。
- **真实业务实例与对照用例**：为主要已接通路径选取代表实例，从业务触发、数据和 ID 一直追到最终结果。对正常、阈值边界、重复、失败、生命周期和重试等适用场景，列「初始状态｜输入与配置｜事件｜决策或返回值｜状态前后值｜下一触发或终止｜验证证据」。覆盖规则优先级和各层交接，区分已静态证实、待联调及待设备验证。用例应可直接用于目标端验收。

## ASCII 流程图

- 详细分析优先画一张端到端总图，再为读者容易误解的阶段分别画子图。按实际链路选择入口与注册、条件分支、数据与状态流、异步回调、失败或重试。跨端对比时可分端画图并标出对应接入点。简单链路用一张图即可，无需凑数量。
- 流程图统一放在等宽 `text` 代码块内，使用 ASCII 连线（如 `|`、`+`、`-->`、`v`）。节点可以用中文和真实类名、方法名。判断分支标明条件与去向，有提前返回、异步回调、重试或重放时画出对应路径。仅展示能够从源码或已观察行为核对的路径，推断单独标明。
- 总图讲阶段如何衔接，子图讲实际判断顺序和状态何时变化。维持适合窄屏阅读的宽度，避免把所有细节挤在一张大图里。图旁给关键源码位置和必要的边界说明。

## 输出和验证

- **关键源码引用配代码摘录。** 在线文档和需独立阅读的报告中，支撑核心结论的 `文件名:行号` 旁必须放适量的代码。选出能够独立说明逻辑的最短片段，保留必要的调用、条件、提前返回、状态写入或后续回调，并解释读者应从中看到什么。多个位置共同说明一条链路时，可在同一代码块按执行顺序摘录，各段标明文件、行号或方法。代码有省略或重组时标为「简化摘录」，保留原有判断顺序；辅助定位的引用可只给位置。

- 对外交付统一使用「Android 代码」「本地可读代码」或「APK 对应的可读代码」，省略代码提取方式的术语。适用于回复、报告、在线文档、标题、图表和代码说明。仍需明确证据范围，例如哪些分支只能从本地代码确认、哪些需要设备或线上配置验证。

- **交付用语。** 严禁在对外文档的标题、正文、图表、代码说明、附录、文件名中出现「反编译」以及反编译相关工具与产物术语，例如 jadx、apktool、class-dump、Hopper、IDA、Ghidra、smali、dex、砸壳、脱壳、dump、伪代码、逆向 等。统一改用「本地可读代码」「本地代码」「分析工程」「可读代码产物」等中性表述；说明证据来源时只写证据范围与位置（类/selector、模块、文件名），不写获取手段。报告交付前逐节自查一次，发现残留即改写或删除。本约束同样适用于发给外部或跨部门的任何版本。

- 关键结论附实际类、方法及文件位置。根据复杂度用调用链、决策表、状态表和简化代码，让读者能看出判断顺序和状态前后值。省略或重组过的代码标注「简化摘录」。
- 明确区分静态事实、推断和运行时验证。按问题给最短的验证路径，例如输入与配置 → 分支 → 请求和缓存 → 页面参数 → 展示或降级。需要现场环境时说明缺什么证据。
- 输出路径格式遵从交付要求。默认在聊天中提供可点击的本地源码位置。
